# Repository Guidelines

## Project Structure & Module Organization

SMAC Native is a C++20 clean-room reimplementation. Public headers live under `include/smac/`, with
deterministic simulation code in `src/core/` and bounded readers in `src/formats/`. `src/tool/`
provides the headless CLI; `src/client/` contains the SDL3 client and fallback stub. Tests are in
`tests/tests.cpp`, fuzz targets and corpora in `fuzz/`, and technical notes in `docs/`.

Keep dependencies flowing from `smac_core` to `smac_formats`, then to `smac-tool` and `smac-native`.
Core code must remain deterministic and free of SDL types and packed source-game structures.

## Build, Test, and Development Commands

Use the checked-in CMake/Ninja presets:

```sh
cmake --preset dev                 # configure a debug build
cmake --build --preset dev         # build libraries, CLI, client, and tests
ctest --preset dev                 # run tests with failures displayed
cmake --build --preset dev --target format-check
```

Before submitting, run the sanitizer gate with `cmake --preset asan`,
`cmake --build --preset asan`, and `ctest --preset asan`. Use the `fuzz` preset and a bounded
`-runs=` count for reader changes. SDL3 dependencies are not fetched by default; configure with
`-DSMAC_FETCH_DEPENDENCIES=ON` when needed. Run the CLI as
`build/dev/smac-tool inspect-map /path/to/map.MP`.

## Coding Style & Naming Conventions

Follow `.clang-format`: LLVM-based style, four-space indentation, attached braces, and a 100-column
limit. Run the `format` target to rewrite C++ files. Match existing conventions: `snake_case` for
functions and files, `PascalCase` for types, and namespaces such as `smac::core`. Compile warnings
include `-Wall -Wextra -Wpedantic -Wconversion -Wshadow`; address warnings rather than suppressing
them. Data-boundary code should return structured `Result<T>` errors instead of throwing.

## Testing Guidelines

The project uses one in-house `CHECK`-based executable (`smac_tests`). Add focused checks to
`tests/tests.cpp`, using generated byte buffers and temporary directories.
Every new parser needs valid, truncated, and malformed-input cases. Do not use proprietary game data
as fixtures. Expand stable-hash and replay checks whenever authoritative state changes.

## Commit & Pull Request Guidelines

Recent commits use short, imperative subjects such as `Decode indexed PCX atlases...`; follow that
style and keep each commit focused. Pull requests should explain behavior and architecture impact,
link relevant issues or roadmap milestones, and report dev, ASan, formatting, and applicable fuzz
results. Include screenshots for renderer changes. Record recovered layouts in `docs/formats/` and
OpenSMACX-derived work in `docs/provenance/OPENSMACX.md`.

## Clean-Room Requirements

Never commit or redistribute original executables, maps, text, fonts, art, audio, or derived assets.
Clearly distinguish faithfully recovered behavior from intentional fixes.
